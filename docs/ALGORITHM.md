# Как устроен `hallucination-probe`

Этот документ объясняет логику проекта «после» — как данные превращаются в результаты, и почему каждый шаг сделан именно так. В конце — пошаговый алгоритм действий, чтобы воспроизвести код.

---

## 1. Что проект делает

Гипотеза: по внутренним состояниям языковой модели **до начала генерации ответа** можно предсказать, что модель сейчас ошибётся. Если это так, мы можем:

- измерить «знание модели о собственной ошибке»;
- сравнить его с обычными методами (энтропия, logprob, самосогласованность), которые работают **после** ответа;
- использовать предсказание риска для адаптивного поиска: искать в Википедии только тогда, когда проба говорит «высокий риск».

Модель: Qwen2.5-Instruct (0.5B / 1.5B / 3B).  
Данные: RuBQ 2.0 (русские/английские фактические вопросы с золотыми ответами и абзацами Википедии).  
Классификатор: линейная логистическая регрессия на скрытых состояниях последнего токена запроса.

## 3. Пошаговое описание модулей

### 3.1 `src/hprobe/data.py` — подготовка вопросов

**Задача:** превратить сырые JSON RuBQ 2.0 в `data/questions.jsonl`.

**Логика:**
1. Читает `RuBQ_2.0_dev.json` и `RuBQ_2.0_test.json`.
2. Фильтрует вопросы:
   - без ответа (`no-answer`) — убираем;
   - больше 5 ответов — убираем (перечисления неоднозначны);
   - тег `count` — убираем (вопросы на подсчёт).
3. Для каждого оставшегося вопроса собирает **все допустимые формулировки ответа**:
   - для URI-ответов: label, русские/английские имена из Wikidata, имена из Википедии;
   - для дат: год;
   - для чисел: число;
   - для текста: текст.
   - добавляет `answer_text` из разметки RuBQ, если есть.
4. Определяет `answer_kind` — большинство среди типов ответов (entity / year / number / text).
5. Определяет `domain` (тематику) по свойствам Wikidata в SPARQL-запросе (география, культура, люди, история, спорт, наука, other).
6. Сохраняет `paragraph_ids` — uid абзацев Википедии, гарантированно содержащих ответ.
7. Делает стратифицированное разбиение 70/15/15 по домену.
   - Важно: один и тот же вопрос (ru + en) всегда попадает в одну часть, иначе получится фальшивый перенос с языка на язык.

**Выход:** `data/questions.jsonl` — по строке на вопрос.

---

### 3.2 `src/hprobe/prompts.py` — единое место для промптов

**Задача:** собирать промпт в формате ChatML с 3 few-shot примерами короткого ответа.

**Логика:**
- `build_messages(question, lang)` — список сообщений: system + 3 пары user/assistant + финальный user.
- `build_prompt(tokenizer, question, lang)` — применяет `chat_template` модели.
- `build_search_prompt(tokenizer, question, paragraphs, lang)` — то же самое, но к финальному вопросу добавляются абзацы Википедии как контекст.
- `clean_answer(text)` — берёт первую непустую строку ответа, убирает `*` и пробелы по краям.

**Почему важно:** любое изменение промпта влияет на сопоставимость прогонов. Поэтому промпт собирается в одном файле и версионируется вместе с кодом.

---

### 3.3 `src/hprobe/generate.py` — прогон модели

**Задача:** получить ответы модели и скрытые состояния **до начала ответа**.

**Логика:**
1. Загружает токенизатор и модель (`AutoModelForCausalLM`).
   - `padding_side = "left"` — критично для извлечения последнего токена запроса.
   - `pad_token = eos_token`, если не задан.
2. Загружает `questions.jsonl`, фильтрует по языку (`question_ru` или `question_en`).
3. Определяет уже обработанные вопросы по `records.jsonl` (`done_uids`).
4. **Не сортирует по длине** — иначе порядок records перестанет совпадать с questions/labels.
5. В цикле по батчам:
   - `run_batch()`:
     - жадная генерация с `output_scores=True`, `output_hidden_states=True`;
     - из `greedy.hidden_states[0]` берётся последний токен каждого примера батча (`[:, -1, :]`); благодаря левому паддингу это всегда последний токен запроса;
     - записываются логарифмы вероятностей и энтропия по токенам ответа — для базовых методов;
     - сэмплируется 5 ответов (`temperature=1.0`, `top_p/top_k` не используются) — для самосогласованности.
   - Каждый батч сохраняется в `chunks/XXXXX.npy`.
   - В `records.jsonl` дописывается по строке на вопрос с полями `uid`, `answer`, `samples`, статистиками и адресом чанка (`chunk`, `row`).
6. В конце `merge_chunks()` собирает `hidden.npy` из чанков **строго в порядке `records.jsonl`**.

**Resume:**
- `done_uids()` читает uid из `records.jsonl`.
- `next_chunk_index()` восстанавливает следующий номер чанка из тех же записей, а не считает файлы в `chunks/`. Это защищает от «висячих» незавершённых чанков.

**Выход:**
- `records.jsonl` — ответы, сэмплы, статистики;
- `hidden.npy` — `[N, L+1, d]` float16, где L — число слоёв, +1 — эмбеддинги;
- `meta.json` — параметры прогона;
- `chunks/` — промежуточные части.

---

### 3.4 `src/hprobe/labeling.py` — проверка короткого ответа

**Задача:** автоматически решить, верен ли ответ модели.

**Логика:**
1. Нормализация: нижний регистр, ё→е, ударения, удаление лишних символов.
2. Стемминг (Snowball) для русского и английского.
3. Правила по типу ответа (`answer_kind`):
   - `entity` / `text` — верно, если значимые слова эталона содержатся в ответе или наоборот (подмножество).
   - `year` — в ответе есть тот же год (3–4 цифры).
   - `number` — в ответе есть число, отличающееся от эталона не более чем на 2 %; также поддерживаются числительные («пять» → 5).
4. Отказ (`"не знаю"`, `"I don't know"` и т.п.) — отдельный флаг, правильным не считается.
5. `answers_agree(a, b)` — согласованность двух ответов модели (для метода самосогласованности).

**Ограничение:** это эвристика. Точность разметки измеряется ручной проверкой 100 ответов (`manual_check.csv`).

---

### 3.5 `src/hprobe/label.py` — разметка прогона

**Задача:** применить `labeling.py` ко всему прогону и собрать `labels.csv`.

**Логика:**
1. Читает `records.jsonl` и `questions.jsonl`.
2. Для каждой записи:
   - `correct` — верен ли жадный ответ;
   - `refused` — это отказ;
   - `consistency` — доля сэмплов, совпадающих с жадным ответом;
   - `samples_correct` — доля сэмплов, верных по эталону;
   - копирует базовые признаки (`mean_logprob`, `entropy` и т.д.).
3. Сохраняет `labels.csv` в том же порядке, что и `records.jsonl` / `hidden.npy`.
4. Создаёт `manual_check.csv` — 100 случайных ответов для ручной проверки.
5. `python -m hprobe.label --run ... --check` сравнивает заполненную ручную разметку с автоматической. Пустые и пробельные строки в `human` игнорируются.

---

### 3.6 `src/hprobe/probes.py` — линейные пробы

**Задача:** предсказать ошибку модели по скрытым состояниям и сравнить с базовыми методами.

**Логика:**
1. Загружает `labels.csv` и `hidden.npy`.
2. Целевая переменная: `error = 1 - correct` (1 — модель ошиблась или отказалась, 0 — верно).
3. `layer_sweep()`:
   - для каждого слоя обучает логистическую регрессию на train;
   - подбирает `C` по ROC-AUC на val (сетка `0.001, 0.01, 0.1, 1.0`);
   - считает AUC на val и test.
4. `summarize()`:
   - считает ROC-AUC базовых методов на test (средний/минимальный logprob, первая вероятность, энтропии, самосогласованность);
   - выбирает **лучший слой по val_auc** (не по test!);
   - переобучает пробу на этом слое и строит 95%-й доверительный интервал бутстрэпом (1000 итераций, seed=42);
   - добавляет строку «Проба, слой X (до ответа)».
5. Сохраняет:
   - `probe/layers.csv` — AUC по слоям;
   - `probe/summary.csv` — итоговое сравнение методов;
   - `probe/layers.png` — график;
   - `probe/probe.npz` — веса лучшей пробы для `search.py`.

**Честность:**
- Слой и регуляризация выбираются по val.
- Test трогается ровно один раз для финальной оценки.
- Бутстрэп даёт ДИ, а не точечную оценку.

---

### 3.7 `src/hprobe/search.py` — адаптивный поиск

**Задача:** использовать пробу как триггер для поиска и построить кривую «точность vs доля поиска».

**Логика:**
1. Загружает:
   - `probe/probe.npz` — веса лучшей пробы;
   - `hidden.npy` — скрытые состояния;
   - `records.jsonl` — текущие ответы;
   - `labels.csv` — эталоны;
   - `data/raw/RuBQ_2.0_paragraphs.json` — абзацы Википедии.
2. `probe_risk()`:
   - берёт скрытые состояния лучшего слоя;
   - нормирует вручную: `(x - mean) / scale` (zero-std защищён заменой на 1);
   - считает логистическую регрессию и возвращает вероятность ошибки.
3. Для каждого порога из сетки (по умолчанию 0.0, 0.05, ..., 0.95, отсортированы по убыванию):
   - `risk >= threshold` — высокий риск, нужен поиск;
   - для отобранных вопросов строится `build_search_prompt()` с абзацами из RuBQ;
   - модель перегенерирует ответы с контекстом;
   - считается общая точность и доля вопросов, для которых включён поиск.
4. Результат сохраняется в `search/curve.csv` и визуализируется в `search/curve.png`.

**Важно:** это потолок. Абзацы берутся из RuBQ и гарантированно содержат ответ. С реальным ретривером кривая будет ниже.

## 5. Ключевые дизайн-решения

1. **Левый паддинг.** В декодере каждый токен видит только предыдущие. С левым паддингом последний токен запроса всегда на позиции `[-1]` в батче.
2. **Не сортировать по длине.** Меньше паддинга ускоряет прогон, но ломает порядок записей. Мы жертвуем скоростью ради корректности.
3. **Test один раз.** Слой и `C` выбираются по val; test используется только для финальной оценки и ДИ.
4. **Линейная проба.** Если сигнал находит простой линейный классификатор, значит информация лежит «на поверхности». Это нижняя граница, а не переобученная модель.
5. **Один факт — одна строка.** Вопрос на ru и en — одна строка в JSONL; split делается по строкам. Иначе проба выучит факт на английском и «узнает» на русском.
6. **Разметка отделена от генерации.** GPU-прогон делается один раз; правила проверки можно править за секунды на CPU.
7. **Адаптивный поиск — потолок.** Используются абзацы из RuBQ, гарантированно содержащие ответ. Это показывает максимальный возможный эффект.

## 6. Алгоритм действий для реализации / запуска

### Этап 0. Окружение

```bash
cd hallucination-probe
python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

### Этап 1. Данные

1. Скачать RuBQ 2.0 в `data/raw/`:
   - `RuBQ_2.0_dev.json`
   - `RuBQ_2.0_test.json`
   - `RuBQ_2.0_paragraphs.json`
2. Подготовить вопросы:
   ```bash
   PYTHONPATH=src python -m hprobe.data
   ```
3. Проверить:
   ```bash
   PYTHONPATH=src python -m pytest tests/test_labeling.py -q
   ```

### Этап 2. Прогон модели (GPU)

```bash
PYTHONPATH=src python -m hprobe.generate \
    --model Qwen/Qwen2.5-1.5B-Instruct \
    --lang ru \
    --out outputs/qwen2.5-1.5b/ru \
    --batch-size 16 \
    --n-samples 5 \
    --max-new-tokens 24 \
    --dtype bf16
```

Если Colab обрывается, просто перезапустить ту же команду — прогон продолжится.

### Этап 3. Разметка (CPU)

```bash
PYTHONPATH=src python -m hprobe.label --run outputs/qwen2.5-1.5b/ru
```

Заполнить `manual_check.csv`, затем:

```bash
PYTHONPATH=src python -m hprobe.label --run outputs/qwen2.5-1.5b/ru --check
```

### Этап 4. Пробы (CPU)

```bash
PYTHONPATH=src python -m hprobe.probes --run outputs/qwen2.5-1.5b/ru
```

Смотреть `probe/summary.csv` и `probe/layers.png`.

### Этап 5. Адаптивный поиск (GPU)

```bash
PYTHONPATH=src python -m hprobe.search \
    --run outputs/qwen2.5-1.5b/ru \
    --model Qwen/Qwen2.5-1.5B-Instruct \
    --lang ru
```

Смотреть `search/curve.csv` и `search/curve.png`.

### Этап 6. Эксперименты

- **В3 (перенос):** обучить пробу на одной тематике/языке, проверить на другой.
- **В4 (размер модели):** повторить этапы 2–5 для Qwen2.5 0.5B, 1.5B, 3B.
- **В5 (адаптивный поиск):** уже реализован в `search.py`.

### Этап 7. Тесты перед публикацией

```bash
PYTHONPATH=src python -m pytest tests/ -q
```

## 7. Частые ловушки

- **Сортировка по длине в `generate.py`.** Убрана; не возвращать, иначе `hidden.npy` и `labels.csv` перестанут совпадать с `questions.jsonl`.
- **Просмотр test перед выбором слоя.** Запрещено: слой и `C` только по val.
- **Изменение промпта без контроля версий.** Промпт влияет на все метрики; менять только осознанно.
- **Использование top-p/top-k в сэмплах.** Мы используем `temperature=1.0` без сэмплера, чтобы измерять внутренний разброс модели.
- **Неправильный паддинг.** Только `padding_side="left"`, иначе последний токен запроса не на фиксированной позиции.
