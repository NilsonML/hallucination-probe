# Что делает ноутбук `01_generate_local.ipynb` (подробное объяснение)

Этот документ — пошаговый разбор: что происходит в каждой ячейке ноутбука, зачем это делается и как связано с научной идеей проекта.

---

## 1. Общая идея (без кода)

Проект проверяет гипотезу:

> **Языковая модель «знает», когда она сейчас соврёт.** Это знание можно увидеть в её внутренних активациях *до того*, как она начала писать ответ.

Если гипотеза верна, мы сможем:

1. Обучить простой классификатор на внутренних состояниях модели и предсказывать, будет ли ответ ошибочным.
2. Сравнить этот метод с обычными способами оценки уверенности модели — вероятностью токенов, энтропией, самосогласованностью.
3. Использовать предсказание риска на практике: например, включать поиск в Википедию только тогда, когда проба говорит «высокий риск ошибки».

**Простая аналогия.** Представьте, что вы спрашиваете человека, а он до ответа на мгновение задумывается. По микровыражению лица можно догадаться: «сейчас скажет уверенно» или «сейчас начнёт гадать». Мы пытаемся поймать такое «микровыражение» у нейросети — только оно записано в тысячах чисел (скрытых состояниях) на последнем токене вопроса.

---

## 2. Данные

Используется датасет **RuBQ 2.0** — русскоязычные фактические вопросы из Wikidata с золотыми ответами и английскими переводами.

После фильтрации остаётся **2327 вопросов** по 7 тематикам (geography, culture, people, history, sport, science, other). Каждый вопрос имеет:

- `question_ru` и `question_en`;
- `gold` — список допустимых формулировок ответа;
- `answer_kind` — тип ответа (`entity`, `year`, `number`, `text`);
- `domain` — тематика;
- `split` — `train` / `val` / `test` (стратифицированное разбиение 70/15/15 по тематике).

**Важно:** один и тот же вопрос на русском и английском всегда попадает в одну часть разбиения. Иначе модель могла бы «выучить» факт на английском train и «показать» его на русском test — фальшивый перенос с языка на язык.

Файл `data/questions.jsonl` уже создан командой `python -m hprobe.data`. В ноутбуке эта команда закомментирована, потому что достаточно сделать её один раз.

## 3. Ячейка 1: импорты и проверка GPU

```python
import os
import sys
import subprocess
import torch
from pathlib import Path

REPO = Path.cwd().parent if Path.cwd().name == 'notebooks' else Path.cwd()
os.chdir(REPO)
sys.path.insert(0, str(REPO / 'src'))

print('GPU доступна:', torch.cuda.is_available())
```

Что здесь происходит:

- `REPO` — путь к корню проекта. Если ноутбук открыт из папки `notebooks/`, то корень — на уровень выше. Иначе корень — текущая папка.
- `sys.path.insert(0, str(REPO / 'src'))` добавляет `src/` в путь поиска модулей, чтобы можно было писать `python -m hprobe.generate` или импортировать `hprobe`.
- `torch.cuda.is_available()` проверяет, видит ли PyTorch видеокарту. Для прогонов с Qwen GPU нужен.

## 4. Ячейка 2 (smoke test): быстрая проверка на 32 вопросах

```python
SMOKE = REPO / 'outputs' / 'smoke'
subprocess.run([
    sys.executable, '-m', 'hprobe.generate',
    '--model', 'Qwen/Qwen2.5-0.5B-Instruct',
    '--lang', 'ru',
    '--limit', '32',
    '--out', str(SMOKE),
    '--batch-size', '8',
], cwd=REPO, env={**os.environ, 'PYTHONPATH': 'src'}, check=True)

subprocess.run([
    sys.executable, '-m', 'hprobe.label',
    '--run', str(SMOKE),
], cwd=REPO, env={**os.environ, 'PYTHONPATH': 'src'}, check=True)
```

### Зачем нужен smoke test?

Прежде чем запускать полный прогон на 2327 вопросах (это занимает десятки минут), полезно убедиться, что всё работает: окружение, GPU, зависимости, разметка.

### Что делает `hprobe.generate`?

Этот скрипт — самый важный в проекте. Он:

1. Загружает модель `Qwen/Qwen2.5-0.5B-Instruct` и токенизатор.
2. Берёт первые 32 вопроса (`--limit 32`).
3. Для каждого вопроса строит промпт через `hprobe.prompts.build_prompt`.
4. Подавает промпт в модель и получает:
   - **жадный ответ** (greedy decoding, `do_sample=False`);
   - **5 сэмплов** с температурой 1.0 (для метода самосогласованности);
   - **вероятности и энтропию** токенов жадного ответа (базовые методы);
   - **скрытые состояния всех слоёв** на последнем токене вопроса.
5. Сохраняет результаты в `outputs/smoke/`.

### Промпт

Промпт собирается как чат:

```
system: Ты отвечаешь на вопросы викторины. Отвечай кратко: только ответ, без пояснений.
user: Какая столица Франции?
assistant: Париж
user: Кто написал роман «Война и мир»?
assistant: Лев Толстой
user: В каком году человек впервые полетел в космос?
assistant: 1961
user: <наш вопрос>
```

Три примера (few-shot) задают формат короткого ответа. Это важно, потому что потом ответ сравнивается с эталоном автоматически.

### Скрытые состояния

Когда модель обрабатывает текст, на каждом слое она преобразует токены в векторы размерности `hidden_size` (например, 896 для 0.5B, 1536 для 1.5B, 2048 для 3B). В `generate.py` мы берём вектор **последнего токена запроса** сразу после того, как модель его обработала, но **до генерации ответа**.

Почему именно последний токен запроса? Потому что в декодере с причинной маской каждый токен видит только предыдущие. Последний токен вопроса «видит» весь вопрос и весь контекст диалога, но ещё не знает, какой ответ модель выберет. Если в активациях этого токена есть сигнал о будущей ошибке — это именно то, что мы ищем.

Паддинг сделан **левым** (`padding_side = "left"`), поэтому последний токен запроса всегда находится на позиции `[-1]` в батче, независимо от длины.

### Что сохраняет `generate.py`?

В папке `outputs/smoke/` появляются:

- `records.jsonl` — по строке на вопрос: вопрос, ответ, 5 сэмплов, статистики токенов, адрес чанка.
- `chunks/00000.npy`, `chunks/00001.npy`, ... — части скрытых состояний по батчам.
- `hidden.npy` — итоговый массив `[N, L+1, d]` float16, собранный из чанков.
- `meta.json` — параметры прогона.

### Что делает `hprobe.label`?

Скрипт сравнивает жадный ответ модели с `gold` из `data/questions.jsonl` и создаёт `labels.csv`:

- `correct` — 1, если ответ верен, 0 — если нет;
- `refused` — 1, если модель отказалась отвечать;
- `consistency` — доля из 5 сэмплов, совпадающих с жадным ответом;
- `mean_logprob`, `min_logprob`, `first_prob`, `first_entropy`, `mean_entropy` — базовые признаки.

Также создаётся `manual_check.csv` — 32 случайных ответа (потому что всего 32) для ручной проверки точности автоматической разметки.

## 5. Ячейка 3: основные прогоны

```python
RUNS = [
    ('Qwen/Qwen2.5-1.5B-Instruct', 'qwen2.5-1.5b', 16),
    ('Qwen/Qwen2.5-0.5B-Instruct', 'qwen2.5-0.5b', 32),
    ('Qwen/Qwen2.5-3B-Instruct',   'qwen2.5-3b',   8),
]

for model, short, bs in RUNS:
    for lang in ['ru', 'en']:
        run_out = OUT / short / lang
        subprocess.run([...generate...])
        subprocess.run([...label...])
```

Эта ячейка запускает "настоящие" эксперименты: три размера модели × два языка.

### Почему именно эти модели?

Вопрос исследования №4: как качество пробы зависит от размера модели? Сравниваются Qwen2.5-Instruct 0.5B, 1.5B и 3B параметров.

### Почему разные batch size?

Большая модель занимает больше видеопамяти. Поэтому для 3B используется меньший батч (`8`), чтобы уместиться в GPU. На GTX 1070 с 8 ГБ даже `8` может быть многовато — при OOM его стоит уменьшить до 4, 2 или 1.

### Как работает возобновление?

`generate.py` умеет докачивать прогон. Он читает `records.jsonl`, находит уже обработанные `uid` и пропускает их. Если Colab/ПК выключился или упал с OOM, достаточно просто перезапустить ту же команду — она продолжит с места остановки.

### Порядок прогонов

В ноутбуке порядок важен: сначала главная модель 1.5B на обоих языках, потом 0.5B и 3B для эксперимента. На практике можно запускать в любом порядке; главное — не удалять папки `outputs/`.

## 6. Ячейка 4: пробы по слоям

```python
for run in sorted(OUT.glob('*/*')):
    if not (run / 'hidden.npy').exists():
        continue
    subprocess.run([
        sys.executable, '-m', 'hprobe.probes',
        '--run', str(run),
    ], ...)
    display(Image(filename=run / 'probe' / 'layers.png', width=600))
```

Это ядро исследования. Скрипт `hprobe.probes` отвечает на вопросы:

- В1: содержат ли скрытые состояния информацию о будущей ошибке?
- В2: на каком слое эта информация выражена сильнее всего?

### Что такое "проба"?

**Проба** — это простой линейный классификатор (логистическая регрессия), который по вектору скрытых состояний одного слоя пытается предсказать, ошибётся ли модель.

Целевая переменная:

```
error = 1 - correct
```

- 1 — модель ответит неверно (или откажется);
- 0 — модель ответит верно.

Для каждого слоя обучается отдельная проба.

### Почему линейная?

Если даже простой линейный классификатор может отличать будущие ошибки от правильных ответов, значит информация лежит "на поверхности" в активациях. Это сильный сигнал: модель действительно "знает" о своей неуверенности. Если бы нужна была огромная нейросеть, это могло бы быть переобучением.

### Как выбирается лучшая проба?

1. **Для каждого слоя** обучается логистическая регрессия на `train`.
2. Параметр регуляризации `C` подбирается по ROC-AUC на `val` (сетка: 0.001, 0.01, 0.1, 1.0).
3. **Лучший слой выбирается по val_auc**, а не по test! Это важно: test используется только один раз для финальной оценки.
4. Для лучшего слоя строится 95%-й доверительный интервал бутстрэпом (1000 итераций).

### С чем сравнивается?

Скрипт считает ROC-AUC нескольких базовых методов, которые работают **после генерации ответа**:

- `-mean_logprob` — средний логарифм вероятности токенов ответа (чем меньше, тем хуже);
- `-min_logprob` — минимальный логарифм вероятности;
- `-first_prob` — вероятность первого токена;
- `first_entropy` / `mean_entropy` — энтропия первого / средняя энтропия токенов ответа;
- `-consistency` — доля сэмплов, совпадающих с жадным ответом (самосогласованность).

Если проба (которая смотрит только на состояния **до ответа**) работает не хуже или лучше этих методов — это главный результат.

### Что получается на выходе?

В папке `outputs/<model>/<lang>/probe/`:

- `layers.csv` — ROC-AUC для каждого слоя;
- `summary.csv` — сравнение всех методов;
- `layers.png` — график;
- `probe.npz` — веса лучшей пробы (понадобится для adaptive search).

## 8. Ячейка 6: адаптивный поиск

```python
subprocess.run([
    sys.executable, '-m', 'hprobe.search',
    '--run', str(OUT / 'qwen2.5-1.5b' / 'ru'),
    '--model', 'Qwen/Qwen2.5-1.5B-Instruct',
    '--lang', 'ru',
], ...)
```

Это ответ на вопрос исследования №5: какая практическая польза?

### Идея

Используем лучшую пробу как триггер:

- Если `probe_risk >= threshold` — модель, скорее всего, ошибётся, поэтому мы **даём ей контекст** из Википедии и просим ответить снова.
- Если риск низкий — оставляем исходный ответ без поиска.

Перебирается сетка порогов (0.0, 0.05, ..., 0.95). Для каждого порога считается:

- `fraction` — доля вопросов, для которых включён поиск;
- `accuracy` — итоговая точность;
- `searched_acc` — точность на вопросах, где был поиск.

Результат — кривая "точность vs доля вопросов с поиском".

### Важное ограничение

В `search.py` абзацы берутся из RuBQ и **гарантированно содержат ответ**. Это "потолок": показывает максимально возможный эффект от идеального поиска. В реальной системе с обычным ретривером кривая будет ниже.

## 10. Если что-то пошло не так

- **OOM при генерации**: уменьшайте `--batch-size` (8 → 4 → 2 → 1).
- **Прогон прервался**: просто перезапустите ту же команду — `generate.py` продолжит с `records.jsonl`.
- **Выключили ПК**: можно включить и продолжить, главное не удалять `outputs/` и `~/.cache/huggingface`.
- **Ошибка в `probes.py`**: убедитесь, что для прогона сначала запущен `hprobe.label` (нужен `labels.csv`).

## 11. Краткий алгоритм "от входа до выхода"

1. Вопрос из `data/questions.jsonl` → промпт с 3 примерами.
2. Промпт токенизируется, подаётся в Qwen.
3. Модель на последнем токене вопроса порождает вектор активаций.
4. Модель генерирует жадный ответ и 5 сэмплов.
5. Ответ сравнивается с эталоном → `labels.csv`.
6. Для каждого слоя обучается логистическая регрессия, предсказывающая `error` по активациям.
7. Лучшая проба сравнивается с базовыми методами.
8. Проба используется как триггер для поиска по Википедии.

---

## 12. Что именно измеряется

- **ROC-AUC** — уменьшается ли проба случайному угадыванию (0.5) или умеет отличать ошибки от правильных ответов (>0.5, чем выше, тем лучше).
- **Test AUC** — финальное качество, измеренное один раз на отложенной выборке.
- **Доверительный интервал (CI)** — насколько устойчива оценка; строится бутстрэпом.
- **Accuracy adaptive search** — насколько вырастает точность, если добавлять поиск для X% самых рискованных вопросов.
